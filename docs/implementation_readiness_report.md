1. 当前仓库的实际文件、Git、配置和测试证据；

3. v1.1 立项设计文档；
4. 本次用户提供的 Phase 0 执行约束；
5. 设计建议和未来规划。

“已设计”不等于“已实现”，“待评审”不等于“已冻结”，“文档中列出测试”不等于“测试已存在或已通过”。

## 3. Phase 0 历史冲突与未冻结口径（已解决）

本节保留 Phase 0 审计轨迹。DEC-01—DEC-10 和 Phase 0.1 合同已经解决下述冲突，当前状态以第 0 节为准。

### 3.1 仓库与项目边界

v1.1 第 17.1 节的 DEC-01 仍允许“同仓独立模块”；本轮明确要求不要混入现有“电力智能运营分析项目”，且当前路径本身是独立目录。建议冻结为**独立 Git 仓库与独立数据域**，仅通过版本化接口或可复制基础组件复用，不共享业务表、迁移、运行证据或作品叙事。

### 3.2 P0 指标数量与清单

v1.1 第 7 章给出 P0 为 12—15 项，第 11 章列出 M001—M018 共 18 项；本轮说明建议首版约 15 项，并单列“可变运营成本”。当前缺少一份唯一、机器可读且获批的 P0 指标清单。建议以 15 项为冻结目标，将“度电成本、站均日收入、枪均日充电量”等候选指标移至 P1，并明确“可变运营成本”的独立口径。

### 3.3 多轮上下文的 P0/P1 边界

v1.1 第 9.2 节将“上下文追问”标为 P1，但第 9.5、12.6 和 15 章又要求 P0 支持结构化会话状态和有限连续追问。建议冻结为：P0 只支持当前会话内的结构化条件继承、显式覆盖和指代解析；跨会话偏好、历史案例检索和记忆管理为 P1。

### 3.4 阶段命名不一致

v1.1 第 16.2 节使用 P0—P5 表示项目阶段，而本轮要求使用 Phase 1—Phase 8；同时 P0/P1/P2 又用于需求优先级。建议后续统一：`Priority P0/P1/P2` 仅表示需求优先级，`Phase 0—8` 表示实施阶段，避免评审和提交记录混淆。

### 3.5 数据表数量描述

v1.1 第 7 章写“4—6 张核心事实/维表”，第 10.2 节列出 10 张建议核心表，记忆设计又增加多张会话与审计表。两者可兼容，但需明确“4—6 张业务主表”与“元数据/运行/记忆治理表”是不同计数口径，并在字段级模型中冻结完整集合。

## 5. Phase 0 历史技术架构结论（已被 v0.1 合同补齐）

v1.1 第 10—15 章中的技术方向总体一致：React/TypeScript、FastAPI/Pydantic/SQLAlchemy、PostgreSQL/pgvector、Redis/Celery、模块化单体、语义层、Query Plan、确定性 SQL 编译、Query Guard、RAG/Answer Guard、分层记忆、审计证据链、Docker Compose/Alembic、pytest/Playwright 没有方向性冲突。

但它仍是“架构草案”，不是“可执行架构基线”，因为：

- 未冻结运行版本、端口、配置键、进程拓扑和开发/测试环境；
- 没有正式 JSON Schema/OpenAPI、错误契约、事件契约和权限策略；
- 没有字段级数据库模型、迁移策略或回滚标准；
- 没有任务队列幂等、重试、死信和事务边界；
- 没有模型网关供应商边界、离线测试替身和降级契约；
- 没有可执行的 SQL 安全策略与负向用例库；
- 没有记忆 P0 的最小数据契约和保留策略批准记录。

详细基线和依赖规则见 `docs/architecture_baseline.md`。
